# 设计决策记录

## D-001：本地处理，云端静态展示

- 日期：2026-07-27
- 状态：已接受
- 决策：Mac 负责解析、AI、分类和构建；线上仅托管静态网站。
- 原因：降低费用、隐私风险和在线运维成本，并保证 Mac 关机后网站仍可访问。

## D-002：专业分类采用严格父子树

- 日期：2026-07-27
- 状态：已接受
- 决策：金融、AI、技术等为一级模块，下面按照用户专业链路逐级递减。
- 原因：用户需要稳定的专业体系，而不是由 AI 自由生成的扁平标签网络。

## D-003：母子树和辅助知识图分离

- 日期：2026-07-27
- 状态：已接受
- 决策：主路径只表达专业归属；跨领域关系使用独立关系边。
- 原因：避免知识关联破坏稳定目录。

## D-004：一级至三级锁定

- 日期：2026-07-27
- 状态：已接受
- 决策：用户定义一级至三级骨架；AI 只在允许的更深层级创建节点。
- 原因：兼顾自动化与分类治理。

## D-005：默认私密，公开采用白名单

- 日期：2026-07-27
- 状态：已接受
- 决策：所有内容默认 `private`，只有显式标记 `public` 才进入公开构建。
- 原因：知识库以后可能包含聊天和金融敏感信息。

## D-006：线上托管优先使用 Cloudflare Pages + Access

- 日期：2026-07-27
- 状态：建议已确认，待实施
- 决策：采用静态 Pages 站点和精确邮箱 Access 策略。
- 原因：免费额度适合个人规模，可私密登录，且不需要在线数据库。

## D-007：账号接入和爬虫暂缓

- 日期：2026-07-27
- 状态：已接受
- 决策：第一阶段先完成本地资料到线上知识库的闭环。
- 原因：先验证核心价值和信息架构，降低首版复杂度。

## D-008：项目统一位于 `$HOME/ai/knowledge`

- 日期：2026-07-27
- 状态：已接受
- 决策：设计、代码、配置、工作流和操作记录都保存在该目录，不修改该目录外的用户文件。
- 原因：用户指定统一位置，便于长期维护和审计。

## D-009：第一版只依赖 Python 标准库

- 日期：2026-07-27
- 状态：已接受
- 决策：核心、静态站点构建、检查与测试均可由 macOS 现有 Python 3.9+ 和 SQLite 运行；Ollama、Cloudflare CLI 等均为可选增强。
- 原因：满足全免费、无需安装、尽量零审批和不修改项目目录外环境的底线。

## D-010：发布动作默认只做预检

- 日期：2026-07-27
- 状态：已接受
- 决策：自动化默认只构建与检查，不连接网络、不登录账号、不发布；真实发布必须由用户以后显式启用并完成 Cloudflare 登录。
- 原因：发布属于外部状态变更，也需要用户自己的云账号；本地闭环不应因此阻塞。

## D-011：发布候选必须是完整构建器产物

- 日期：2026-07-30
- 状态：已接受
- 决策：发布门禁核验 visibility、文档可见性、内容摘要、计数和完整文件白名单；额外文件或构建后篡改均阻止发布。
- 原因：通用凭据正则不能证明 public 包没有混入 private 内容。

## D-012：退休分类节点的资料迁入“待归类”

- 日期：2026-07-30
- 状态：已接受
- 决策：分类节点删除或停用时，已有资料自动移动到“待归类”、删除旧索引并重新排队。
- 原因：不能静默隐藏资料，也不能生成引用不存在节点的网站数据。

## D-013：自动输入不跟随符号链接

- 日期：2026-07-30
- 状态：已接受
- 决策：显式 symlink 输入被拒绝，收件箱扫描中的 symlink 被跳过；raw 读取必须位于项目 `data/raw/`。
- 原因：项目收件箱不能成为读取项目外敏感文件的间接通道；迁移后 raw 边界为 `workspace/data/raw/`。

## D-014：公开仓库采用 Apache License 2.0

- 日期：2026-08-09
- 状态：已接受
- 决策：项目以 `Eascaty/personal-knowledge-os` 公开，并采用 Apache License 2.0。
- 原因：在允许使用、修改和分发的同时提供明确的专利授权条款，适合长期维护的开源工程。

## D-015：保留 Python MVP，增量增加 Java 服务

- 日期：2026-08-09
- 状态：已接受
- 决策：保留已经验证的 Python 标准库流水线，后续以 Java 21 + Spring Boot 模块逐步承接领域 API、搜索、导入和部署能力。
- 原因：避免为了技术栈展示推倒有效实现；让每次 Java 迁移都有真实业务价值、测试和可解释的 GitHub 记录。

## D-016：Java J1 只读且仅暴露公开知识

- 日期：2026-08-09
- 状态：已接受
- 决策：Java 21 服务只读现有 SQLite schema v1；知识列表、详情和搜索仅返回 `public` 条目，来源不返回原始路径；HTTP 默认只监听 `127.0.0.1`。
- 原因：先建立稳定的领域/API 契约，同时保持 Python 写入链路的单一所有权，避免双写、隐式迁移和私人资料泄露。

## D-017：公开仓库采用受保护主分支与可复现构建

- 日期：2026-08-09
- 状态：已接受
- 决策：`main` 只允许通过 Java/Python 四项 CI 与 Public Demo 构建的 PR 普通合并；禁止强推、删除、squash 和 rebase。Java 使用带 SHA-256 的 Maven Wrapper，并在 CI 中强制覆盖率门槛。
- 原因：保留分步工程记录、防止绕过验证，并让新环境无需依赖未知 Maven 版本即可复现构建。

## D-018：公开 Demo 与真实个人知识完全隔离

- 日期：2026-08-10
- 状态：已接受
- 决策：GitHub Pages 只发布由3份固定虚构测试资料在临时目录生成的 public 站点；不从维护者本机数据库或知识目录生成公开 Demo。
- 原因：让访客可以直接体验项目，同时保持默认私密、公开白名单和公开仓库不含真实个人知识的安全边界。

## D-019：采用模块化单仓库并减少重复留痕

- 日期：2026-08-10
- 状态：已接受
- 决策：保留 Python 流水线、Java API 和 Web/PWA 的单仓库协作，但通过 `apps/`、`packages/contracts/` 与 `workspace/` 建立清晰边界；Git 提交与 PR 记录普通实现过程，状态、决策和操作文档只记录各自负责的事实。
- 原因：现有功能可靠，但扁平大模块、源码与生成物混放、重复配置和每次改动强制多文档留痕增加了 AI 误改、分支膨胀和文档漂移风险。

## D-020：跨应用契约集中版本化

- 日期：2026-08-10
- 状态：已接受
- 决策：canonical JSON Schema 与只读 HTTP OpenAPI 统一保存在 `packages/contracts/`；Python、Java、Web 和未来 App 只通过版本化契约协作，v1 的破坏性变化必须升级主版本。
- 原因：让多个应用可以独立演进和部署，同时防止字段漂移、隐私边界分叉及未来 App 反向绑定某个实现细节。

## D-021：先固化 App 适配边界，不创建空移动端工程

- 日期：2026-08-10
- 状态：已接受
- 决策：现阶段由 PWA 提供跨设备体验，Web 同时支持静态包与 API v1；未来原生 App 通过 OpenAPI v1 接入，不直接访问 SQLite。目标平台与同步需求确定后再创建 `apps/mobile/`。
- 原因：项目已经具备可安装 PWA，提前引入移动端框架会增加重复实现和维护成本，却无法在产品需求未定时形成有效能力。

## D-022：Java J2 复用 SQLite FTS5，不引入 Lucene

- 日期：2026-08-12
- 状态：已接受
- 决策：Java 搜索服务复用 Python 流水线维护的 SQLite FTS5 trigram 索引，以 BM25 排序，并为短查询、特殊语法和无 FTS 命中保留参数化 LIKE 降级路径；当前不引入 Lucene。
- 原因：现有单机知识库已经具备中文索引，复用同一事实来源可以保持零新增运行依赖和只读边界；等数据规模、分词质量或横向扩展需求超过 SQLite 能力时再评估独立搜索引擎。

## D-023：J3 采用受限离线 Java 导入，不开放双写服务

- 日期：2026-08-12
- 状态：已接受
- 决策：允许独立 Java CLI 复用 schema v1 导入本地文件，但仅创建不可变 raw、source、初始 extract 任务和审计事件；Python 继续独占 schema、任务处理、分类与发布，HTTP API 不增加写端点。两种运行时通过同一个 POSIX 项目锁互斥。
- 原因：这能验证 Java 的幂等事务能力并提供可选 CLI，同时把写入面限制在已有入队契约内；共享锁和禁止 HTTP 写入避免并发双写、远程攻击面与处理逻辑分叉。

## D-024：J4 容器只承载只读 API，不把私密工作区打入镜像

- 日期：2026-08-12
- 状态：已接受
- 决策：Java API 采用固定 Temurin 21、多阶段、非 root 容器；构建上下文排除整个私密工作区，运行时只读挂载经过验证的 SQLite 快照。Compose 默认只绑定回环地址，并以 Actuator liveness/readiness 区分进程存活与 schema v1 数据库可用。
- 原因：容器首先解决可重复运行、最小权限和平台健康判断，不应顺带扩大数据暴露或远程攻击面。公网认证、TLS 和同步需要基于真实访问者与 App 需求单独设计。

## D-025：正式版本只从 main 的一致 tag 自动生成并证明来源

- 日期：2026-08-23
- 状态：已接受
- 决策：软件 Release 只接受已经合入 `main`、并与 Python、Java、运行时及 CHANGELOG 一致的语义版本 tag；GitHub Actions 重新执行核心门禁，生成版本化 JAR、SHA-256 与 build provenance，不接受人工替换的未验证产物。
- 原因：源码版本已经演进到0.4.0，但人工构建无法稳定证明产物对应哪个提交。把版本一致性、测试、校验和与来源证明放入受限工作流，可减少版本漂移和供应链误发布，同时不触碰任何真实知识数据。

## D-026：日常本地运行由项目内知识管家编排

- 日期：2026-08-23
- 状态：已接受
- 决策：使用纯 Python 项目内单实例管理器监听收件箱、调用既有全流水线并提供静态网站；macOS 提供双击入口。服务和控制接口只绑定回环地址，停止请求必须匹配私密状态中的实例与令牌，失败时继续提供上一版成功网站。Docker、系统级安装和开机自启都不是日常流程的前置条件。
- 原因：用户需要全免费、低操作成本和不依赖外部平台的自动闭环，同时要求不修改项目目录外环境。复用现有流水线可以避免第二套处理逻辑，项目内后台进程也比每次手工运行处理和预览命令更符合日常使用。
